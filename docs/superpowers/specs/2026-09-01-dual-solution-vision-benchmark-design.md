# 双方案错题视觉识别基准设计

## 1. 目标

在不修改生产识别流程的前提下，对 `old_solution` 与 `main` 两个分支进行可复现、可合并的错题区域识别对比，回答两个问题：

1. 每套方案是否以允许误报的方式覆盖全部真实错题区域。
2. 为获得该召回率，每页图片付出了多少处理时间和多少次 LLM 请求。

本轮只收敛诊断与测试工具，不把实验方案接入生产任务。

## 2. 非目标

- 不在两个分支之间复制或混用识别实现。
- 不使用 page33～35 的固定位置、固定数量或专用提示词规则。
- 不用 CV 组件数量代替错题数量。
- 不把本地 OCR 结果作为错题区域是否命中的决定条件。
- 不在本轮调整生产服务、部署脚本或环境变量。

## 3. 分支职责

### 3.1 `old_solution`

增加只读基准适配器，调用该分支原有的整页识别、红色证据过滤和整页定位能力，输出统一格式的错题候选区域。

适配器不得改变旧方案 prompt、过滤阈值或生产调用路径。若为记录原始 LLM 请求与响应而需要包装客户端，只允许在诊断脚本进程内完成。

### 3.2 `main`

在现有诊断实验中冻结一个简化方案：

1. 本地 CV 生成红叉候选。
2. LLM1 核验候选，并保留满足配置条件的高风险/高几何分候选。
3. LLM2 对保留候选只执行一轮错题区域定位。
4. 后置逻辑只做审计、聚类和统计，不通过额外 LLM 重试改变结果。

本轮移除或关闭固定第二轮 LLM2、定向第二轮 fallback 等重试路径，以形成可解释的单轮候选基线。红圈、老师批注和作答内容可以作为 LLM2 的通用定位辅助，但不能成为硬性存在条件。

所有阈值继续来自外部配置文件，并在配置文件中说明含义。

## 4. 统一命令与输入

两个分支提供同名入口：

```text
scripts/benchmark_vision_solution.py
```

入口接受相同参数：

```text
page33=/diagnostic-input/page33.jpg
page34=/diagnostic-input/page34.jpg
--truth-regions /diagnostic-input/truth-regions.json
--subject chinese
--output /diagnostic-output/<run-name>
```

图片标签不限制为 page33～35；后续新增图片只需增加 `label=path` 参数，并在真值文件中提供对应区域。

`--expected` 可继续兼容，但仅用于数量一致性提示。准确率计算以 `truth-regions.json` 中每道错题的身份和区域为准。

## 5. 真值与命中规则

每个真实错题必须有稳定的 `truth_id` 和归一化区域框：

```json
{
  "page33": [
    {"truth_id": "page33-q1", "bbox": [0.1, 0.2, 0.3, 0.4]}
  ]
}
```

预测区域与真值区域的匹配阈值来自独立基准配置文件，不写死在代码中。报告至少区分：

- 真值命中数和真值召回率；
- 未命中的 `truth_id`；
- 未匹配预测区域，即误报候选；
- 多个预测区域重复覆盖同一真值；
- 一个预测区域跨越多个真值的归属异常。

首要收敛标准是每次运行的真值召回率为 1.0；允许误报，但必须量化误报数量和重复归属。

## 6. 公平耗时口径

核心对比只覆盖“输入整页图片到输出错题区域”的分支原生区域识别流程。本地 OCR 不计入核心区域识别耗时，也不影响区域命中判定；如某分支执行了 OCR，则单独列出，不并入核心指标。

每页记录：

- 区域识别墙钟总耗时；
- 本地 CV 耗时；
- 各 LLM 阶段耗时；
- 后置审计耗时；
- LLM 请求总次数；
- 单次 LLM 请求明细。

汇总报告记录每套方案的平均耗时、P50 和最差耗时。首次联调每个分支运行一次；正式判断随机容忍度时，使用同一数据集分别连续运行至少三次，再合并统计成功率与耗时波动。

## 7. 统一产物协议

每次运行至少生成：

```text
manifest.json
summary.json
comparison-report.md
timing-report.md
pages/<label>/predictions.json
pages/<label>/truth-audit.json
pages/<label>/timing.json
pages/<label>/raw-llm-calls/
pages/<label>/annotated-predictions.jpg
```

`manifest.json` 包含：

- `schema_version`；
- `solution_id`：`old_solution` 或 `main_single_pass`；
- 当前 Git commit；
- 诊断配置摘要或哈希；
- 图片及真值文件摘要或哈希；
- 开始时间与运行环境信息。

若容器中无法读取 Git 元数据，commit 字段允许为空，但 `solution_id` 必须由分支内适配器明确声明，禁止根据输出结果猜测。

## 8. 离线合并分析

提供一个不调用 LLM 的离线比较入口，读取两个或多次运行的解压目录，校验 `schema_version`、输入图片摘要和真值摘要一致后，生成：

- 两套方案逐页、逐真值的命中对照；
- 每次运行的召回、误报和重复归属；
- 多轮运行的全真值覆盖成功率；
- 平均、P50、最差耗时及 LLM 请求数；
- 准确率收益与耗时增量的并列表格。

输入摘要不一致时应明确报错，避免把不同图片或不同真值的结果合并。

## 9. 实施顺序与验收

1. 在 `old_solution` 增加统一基准适配器和测试。
2. 在隔离的 `main` worktree 中将诊断方案收敛为单轮候选方案，并增加同协议适配器和测试。
3. 两个分支分别验证 CLI 帮助、固定样例的产物 schema、真值审计和计时字段。
4. 用户补充新图片及真值后，服务器分别切换两个分支，使用同一命令运行。
5. 使用离线工具合并两个压缩包，比较准确率与耗时。

完成标准：

- 两个分支可使用相同命令和真值文件运行；
- 产物协议一致且包含原始证据；
- `main` 不再执行第二轮 LLM2；
- 报告能定位到具体漏检的 `truth_id`，而不是只比较数量；
- 报告能同时给出召回、误报、请求数和耗时；
- 生产识别代码行为保持不变。
